# Google Sheets Setup

## Назначение

Этот файл теперь работает как справочник по `Google Sheets + Apps Script` для проекта.

Сам код `Apps Script` вынесен в отдельный файл:

- [google_sheets/Code.gs](D:/DEV/BSPRJ/google_sheets/Code.gs)

Это основной файл, который нужно копировать в `Apps Script`.

## Что где лежит

- `google_sheets/Code.gs`
  - готовый код `Apps Script`
  - источник правды для логики таблицы, аналитики и оформления
- `GOOGLE_SHEETS_SETUP.md`
  - инструкция
  - расшифровка названий
  - порядок развёртывания и обновления

## Быстрый сценарий

Если нужно просто обновить таблицу:

1. Открой Google Sheet.
2. Перейди в `Расширения -> Apps Script`.
3. Открой файл `Код.gs`.
4. Удали старое содержимое `Код.gs`.
5. Открой локальный файл [google_sheets/Code.gs](D:/DEV/BSPRJ/google_sheets/Code.gs).
6. Скопируй весь код из `Code.gs`.
7. Вставь в `Код.gs`.
8. Нажми `Сохранить`.
9. Обнови развёртывание веб-приложения.
10. Вернись в таблицу и перезагрузи страницу.
11. Нажми `⚙️ BS -> Refresh latest data`.

## Как разворачивать

### Где нажимать

1. `Развертывание`
2. `Управление развертываниями`
3. Найди текущее `Веб-приложение`
4. Нажми значок карандаша
5. Нажми `Развернуть`

### Что значит "карандаш"

`Карандаш` в окне `Управление развертываниями` означает:

- редактировать текущее развёртывание
- выпустить новую версию этого же `Apps Script`
- применить изменения из нового кода

### Что значит "новая версия"

Когда ты сохраняешь новый `Code.gs`, Google ещё не всегда сразу применяет его к веб-приложению.

`Новая версия` в развёртывании нужна, чтобы:

- обновить серверную логику `doPost(...)`
- обновить меню и аналитику
- сделать так, чтобы устройство и таблица работали уже с новым кодом

Если код поменялся, а развёртывание не обновили, таблица может вести себя "как раньше".

## Что получится в таблице

### Сырой слой

- `log`
  - активный текущий день
  - сюда пишет устройство
  - стиль этого листа считается удачным и аналитический код его не ломает
- листы вида `14-05-2026` или `2026-05-14`
  - архив завершённого дня
  - это тоже сырой слой, не итоговая аналитика

### Технический слой

- `clean_summary_10m`
  - очищенный слой по 10-минутным окнам
  - здесь убираются повторы по ключу
  - здесь видно, какие окна валидные, а какие нет
  - здесь видно пропуски и проблемные места
  - это лист для проверки, а не главный лист чтения

### Основной аналитический слой

- `summary_daypart`
  - главный лист чтения аналитики
  - показывает агрегаты по `DAY / EVE / NGT`
- `summary_levels`
  - показывает распределение `SILENT / NORMAL / LOUD / PEAK`
- `summary_health`
  - показывает качество данных: дубли, малые выборки, пропуски, покрытие
- `summary_conclusions`
  - короткий человеко-понятный итог по `DAY / EVE / NGT`
  - сводит вместе средний относительный уровень, типичный уровень и уверенность по покрытию

### Витрина

- `charts`
  - быстрый обзорный экран
  - подходит для "быстро посмотреть общую картину"
  - точные числа лучше смотреть в `summary_*`

## Расшифровка названий листов

### Сырой слой

- `log` = active live log, текущий активный день
- `14-05-2026` = archived completed day, архив завершённого дня

### Аналитика

- `clean_summary_10m`
  - `clean` = очищенный
  - `summary` = итог по строкам
  - `10m` = окно 10 минут
- `summary_daypart`
  - итог по частям суток
- `summary_levels`
  - итог по уровням шума
- `summary_health`
  - итог по качеству данных
- `summary_conclusions`
  - короткий итог для быстрого чтения
- `charts`
  - визуальный обзор

## Расшифровка названий колонок

## Словарь состояний

В проекте используются две разные группы состояний, и их не нужно смешивать:

- `CLIP / LOW / OK`
  - это техническое состояние входного сигнала
  - помогает понять, насколько надёжен сам вход микрофона
  - `LOW_HOLD` и `CLIP_HOLD` означают уже не краткий эпизод, а устойчивую проблему сигнала

- `SILENT / NORMAL / LOUD / PEAK`
  - это пользовательский уровень шума
  - помогает понять наблюдаемый уровень, а не качество входа

Короткое правило:

- `CLIP / LOW / OK` = signal quality state
- `SILENT / NORMAL / LOUD / PEAK` = user-facing noise level

### Базовый лог

- `DEV ID` = идентификатор устройства
- `VER` = версия прошивки
- `BUILD` = номер сборки
- `DATE` = дата окна
- `T FROM` = начало окна
- `T TO` = конец окна
- `PART` = часть суток: `DAY`, `EVE`, `NGT`
- `NOW %` = средний текущий относительный уровень за окно
- `H %` = средний часовой уровень за окно
- `M %` = средний уровень с начала работы
- `RAW MIN` = минимум сырого сигнала
- `RAW MAX` = максимум сырого сигнала
- `AVG P2P` = среднее peak-to-peak значение
- `SIG IN` = итоговая метка качества входного сигнала (`OK`, `LOW`, `CLIP`, `LOW_HOLD`, `CLIP_HOLD`)
- `TEMP C` = средняя температура
- `HUM %` = средняя влажность
- `WIN MIN` = длина окна в минутах
- `QUIET` = число тихих сэмплов
- `LOUD` = число громких сэмплов
- `SAMPLES` = сколько сэмплов вошло в окно
- `UPTIME` = сколько устройство живёт с последней перезагрузки, в компактном виде `0 d, 3 h, 14 m`

### Технические колонки в `clean_summary_10m`

- `LEVEL` = человеко-понятный уровень по `AVG P2P`
- `SOURCE SHEET` = из какого листа пришла строка
- `DAY STATE` = `CURRENT` или `ARCHIVE`
- `RECORD KEY` = уникальный ключ окна
- `DUP COUNT` = сколько раз такое окно встретилось
- `IS DUPLICATED` = есть ли дубль
- `IS VALID` = проходит ли окно фильтр качества
- `GAP BEFORE` = сколько окон пропущено перед этой строкой
- `QUALITY` = короткая итоговая оценка строки

### Аналитические колонки

- `WINDOWS TOTAL` = сколько уникальных окон найдено
- `WINDOWS VALID` = сколько окон прошло фильтр
- `EXPECTED WINDOWS` = сколько окон ожидалось по этому временному блоку
- `COVERAGE %` = насколько данные покрывают ожидаемый объём
- `MISSING WIN` = сколько окон пропущено
- `SIGNAL ISSUE WIN` = сколько окон имели `SIG IN`, отличный от `OK`
- `ENV FAIL WIN` = сколько окон содержали ошибки SHT31
- `ENV FAIL SAMPLES` = суммарное число неудачных чтений SHT31
- `MIN FREE HEAP` = минимальный heap за день
- `RESET ISSUE WIN` = сколько окон относились к boot-сессии после `WDT`, `PANIC`, `BROWNOUT` или другой проблемной перезагрузки
- `SILENT WIN / NORMAL WIN / LOUD WIN / PEAK WIN`
  - сколько валидных окон попало в этот уровень
- `MAIN LEVEL` = какой человеческий уровень чаще всего встречался в этой части суток
- `MAIN SHARE %` = какую долю валидных окон занял этот типичный уровень
- `CONFIDENCE`
  - `GOOD` = покрытие достаточно уверенное
  - `PARTIAL` = данные уже полезны, но день закрыт неполно
  - `WEAK` = вывод пока ранний
- `READING` = готовая короткая текстовая формулировка для быстрого понимания

## Что считается валидным окном

Текущее правило:

- валидное окно = `SAMPLES >= 100` и `SIG IN` пустой для старой совместимой строки либо равен `OK`
- `ENV FAIL` сохраняется как отдельный диагностический флаг и не удаляет акустическое окно автоматически

Это настраивается в коде строкой:

- `const MIN_VALID_SAMPLES = 100;`

## Визуальный стандарт Google Sheets

### Что не трогаем

- стиль `log`
- стиль архивных сырых листов

### Что оформляем отдельно

- `clean_*`
  - как спокойный технический слой
  - часть служебных колонок скрыта по умолчанию
- `summary_*`
  - как читаемый аналитический слой
  - цвет должен помогать понять смысл групп колонок
- `charts`
  - как обзорный экран
  - не как просто лист с сырыми служебными блоками
  - helper-данные могут лежать в скрытых служебных колонках
  - рабочая зона должна быть компактной, без больших пустых областей
  - если встроенные charts Google Sheets ведут себя нестабильно, дашборд может использовать ячеечные мини-диаграммы вместо плавающих chart-объектов

### Цветовая идея

- зелёно-синие блоки = идентификация и дата
- жёлтые блоки = проценты и уровни
- оранжевые блоки = амплитуда и raw-параметры
- зелёные блоки = температура и влажность
- розово-красные блоки = quiet/loud/quality/risk
- серые блоки = служебные или технические части

## Telegram

### Что уже умеет Apps Script

Сейчас Telegram сделан как ручной внешний отчётный слой поверх `summary_*` и `clean_summary_10m`.

В меню `⚙️ BS -> Reports` есть:

- `Send latest Telegram status`
- `Send daily Telegram summary`

В техническом режиме меню `⚙️ BS · TECH -> Automation` также содержит:

- `Enable auto daily summary`
- `Disable auto daily summary`

Ручные команды отправляют отчёт сразу. Автоматический отчёт работает через отдельный hourly trigger.

### Как настроить Telegram

Секреты не нужно хранить в коде `Code.gs`.

Используются `Script Properties`:

- `BS_TELEGRAM_ENABLED`
- `BS_TELEGRAM_BOT_TOKEN`
- `BS_TELEGRAM_CHAT_ID`
- `BS_TELEGRAM_AUTO_DAILY_ENABLED`

### Где это задавать

1. Открой `Расширения -> Apps Script`
2. Нажми `Project Settings`
3. Найди блок `Script properties`
4. Добавь свойства:
   - `BS_TELEGRAM_ENABLED` = `true`
   - `BS_TELEGRAM_BOT_TOKEN` = токен бота
   - `BS_TELEGRAM_CHAT_ID` = chat id
   - `BS_TELEGRAM_AUTO_DAILY_ENABLED` = `false`
5. Сохрани

### Как это работает

- `Send latest Telegram status`
  - берёт последнюю валидную строку из `clean_summary_10m`
  - отправляет краткий текущий статус
- `Send daily Telegram summary`
  - берёт последний доступный день из `summary_daypart`, `summary_levels`, `summary_health`
  - отправляет краткую дневную сводку
- Все Telegram-уведомления
  - внизу добавляют аккуратную ссылку `Online Statistics`
  - ссылка ведёт сразу в рабочую Google Sheets-таблицу
- `Enable auto daily summary`
  - включает hourly background trigger
  - сам шлёт сводку по последнему архивному дню только один раз
- `Disable auto daily summary`
  - удаляет этот trigger и выключает авто-режим

### Что дальше планируется

Следующая согласованная последовательность такая:

1. Ручной `Latest status`
2. Ручной `Daily summary`
3. Проверка формата сообщений
4. Автоматический `daily summary`
5. `anomaly / bad data alerts`

### Как работает автоматический `daily summary`

Авто-режим не шлёт текущий живой `log`.

Он работает по последнему архивному дню:

- ищет последний архивный лист
- ждёт завершения уже запущенного автоматического обновления аналитики
- использует готовую аналитику без повторной тяжёлой перестройки
- пересобирает аналитику только как запасной вариант, если новый архив уже есть, а его сводка ещё не готова
- отправляет сводку только один раз на этот день
- записывает день как отправленный только после подтверждения Telegram Bot API

Это сделано через hourly background trigger, а не через жёсткое время, чтобы сводка не ломалась, если архив нового дня появился не ровно в полночь.

## Режимы интерфейса

Для обычного просмотра нажми `Switch to User mode`, если сейчас открыт технический режим.

Название меню всегда показывает текущий режим: `⚙️ BS · USER` или `⚙️ BS · TECH`. Внутри меню строка с `●` обозначает активный режим, а отдельная строка `Switch to ...` выполняет переключение.

Останутся видимыми:

- `log`
- `daily_verdict_table`
- `charts`

Архивные листы, внутренние аналитические листы и технические колонки будут скрыты, но не удалены.

Для полного анализа и обслуживания нажми `Switch to Technical mode`. Этот режим показывает все архивные и аналитические листы, возвращает все колонки и открывает служебные подменю `Maintenance`, `Diagnostics` и `Automation`.

В `Automation` каждая настройка имеет информационную строку `● ...: ON/OFF` и отдельную команду `Turn ON ...` или `Turn OFF ...`. Нажатие на строку с `●` только показывает общий статус и не пересоздаёт триггер. После переключения меню обновляется сразу.

В `Diagnostics` точка также показывает фактическое состояние таблицы:

- `● Technical columns: SHOWN/HIDDEN/MIXED/NONE`
- `● Archive sheets: SHOWN/HIDDEN/MIXED/NONE`
- `● Analytics sheets: SHOWN/HIDDEN/MIXED/NONE`

`SHOWN` означает, что всё показано; `HIDDEN` — всё скрыто; `MIXED` — показана только часть; `NONE` — соответствующих листов или колонок пока нет. Для `SHOWN/HIDDEN` меню предлагает только противоположное действие, для `MIXED` — обе команды. Строка с `●` ничего не меняет.

## Как очистить таблицу перед чистым прогоном

Перед финальным прогоном можно использовать меню `⚙️ BS -> Danger zone -> Reset for clean run`.

Команда делает следующее:

- очищает активный лист `log` до заголовка
- удаляет все архивные дневные листы вида `14-05-2026` или `2026-05-14`
- очищает и пересоздает пустые аналитические листы `summary_*`, `daily_verdict*`, `clean_summary_10m`, `charts`
- не трогает `Script Properties`, поэтому Telegram token/chat id и auto-summary настройки сохраняются

Защита от случайного удаления:

- нужно подтвердить окно `YES / NO`

Перед нажатием `Reset for clean run` сохрани старые данные отдельно, если они еще нужны для истории. После очистки начни чистый прогон с физического power-cycle контроллера, чтобы `boot_seq`, uptime и первые строки нового прогона были понятными.

## Как убрать технический шум из таблиц

Для обычного просмотра используй `Switch to User mode`.

Команда скрывает, но не удаляет технические колонки:

- прошивочные маркеры и внутренние проценты
- сырые min/max и P2P-диагностику
- duplicate/gap helper поля
- флаги графиков и служебные счетчики
- heap/reset/boot поля в сырых логах

Расчеты и финальная проверка от этого не ломаются: данные остаются в таблицах. Для полного разбора после прогона нажми `Switch to Technical mode`.

## Что проверять после обновления

1. `log` выглядит как раньше
2. `clean_summary_10m` не выглядит как главный лист
3. `summary_daypart` читается как основной итог
4. `summary_levels` быстро показывает смесь уровней
5. `summary_health` быстро показывает качество данных
6. `summary_conclusions` даёт самый быстрый человеческий вывод без ручной сборки из нескольких листов
6. `charts` подходит для быстрого обзора и не разбрасывает полезные блоки по пустому листу
7. даже без встроенных chart-объектов `charts` должен оставаться полезным за счёт KPI и мини-диаграмм в ячейках

## Типовые проблемы

### Не появилось меню `⚙️ BS`

- страница таблицы не была обновлена после сохранения скрипта

### Таблица ведёт себя по-старому

- обновлённый `Code.gs` не был сохранён в Apps Script
- страница Google Sheets не была перезагружена после сохранения

### Не создаются `summary_*`

- `Rebuild analytics` не был выполнен
- или `Apps Script` завершился с ошибкой

### Слишком много колонок в `clean_summary_10m`

- часть служебных колонок скрыта по умолчанию
- если нужно, их можно вернуть через `Показать столбцы`

### Хочется убрать аналитику и оставить только лог

- используй `Switch to User mode`
- режим скрывает внутренние аналитические и архивные листы, но не удаляет их

## Примечания

- Активный лист для записи всегда называется `log`
- При реальной смене дня старый `log` уходит в архив, а новый день продолжает жить в `log`
- Если архивный лист уже существует, строки аккуратно дописываются туда, а не создаётся отдельный дубликат-лист
- Локальный `LittleFS` лог всё ещё полезно держать как резервный канал

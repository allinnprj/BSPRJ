## Important Decisions

- C3's own Telegram OTA flow is the only planned C3 upload method. BS must not proxy OTA or manage C3 Wi-Fi; `/c3ota`, OTA_ON, WIFI_OFF, TREQ/TIME, and Gateway/Service runtime behavior are retired. `RESTART`, Charge/mode/GPS/sleep controls remain outside the BS command path.
- Hardware wake is deliberately separate from status: `/c3wkp` owns the BS GPIO23 pulse, while `/c3sts` remains status-only. Wake uses C3 GPIO5 with an external `10 kOhm` pull-up to C3 `3.3 V`, BS GPIO23 open-drain, optional `1 kOhm` series protection, and common GND; connection and continuity checks are a later powered-off physical stage.
- GPS FIX is intentionally a one-time manual commissioning action, not a dynamic or periodically refreshed function: obtain and save a valid FIX once, then reuse the persisted location indefinitely. Do not add automatic GPS acquisition or scheduled FIX refresh; change the saved FIX only by an explicit manual action if the physical device is relocated.

- Canonical controller names are fixed: `BS` means the main BSPRJ ESP32-WROOM-32U noise/network/logging gateway, and `C3` means the autonomous ESP32-C3 SuperMini INA3221/Solar Control/GPS/sleep controller. Use `WROOM` or `SuperMini` only for hardware-specific discussion; do not rename existing device IDs, source classes, files, or wiring labels.

- Before integrating larger modules, keep memory decisions incremental: ESP-NOW first is acceptable, GPS should use a compact parser, and GSM needs a separate memory/architecture plan before implementation. A single PlatformIO project with multiple controller environments is allowed later if it helps manage both BSPRJ controllers together.
- If SHT31 data still disappears, use `env_fail_count`, `SHT31_LOST/SHT31_REINIT/SHT31_RECOVER`, and restart rows to decide whether the issue is sensor/I2C/power/contact related before soldering.
- Use `DATA_DICTIONARY.md` or `DATA_DICTIONARY_RU.md` when the user asks what a column, status, verdict, flag, or Telegram line means.
